# 🚀 Internship Project Documentation

## AI-Based Startup Screening & Evaluation System

---

# 1. 📌 Project Overview

This project is an **automated startup screening system** designed for incubation centers (like RIIDL).

The system evaluates startup applications by analyzing their **pitch decks (PPT/PDF)** and generates:

* Structured scores
* Decision (Select / Reject / Pre-incubation)
* Reasoning

The goal is to **reduce manual effort** and ensure **consistent evaluation of startups**.

---

# 2. 🎯 Problem Statement

Incubation centers receive **large volumes of startup applications**, making manual evaluation:

* Time-consuming
* Inconsistent
* Dependent on human bias

👉 There was a need for a system that:

* Automates screening
* Maintains evaluation consistency
* Works in real-time with incoming applications

---

# 3. 🏗️ System Architecture (Current)

### 🔹 Data Flow:

HTML Form (RIIDL Website)
→ AWS DynamoDB (`startups` table)
→ Python Worker (`ppt_worker.py`)
→ AI Evaluation
→ DynamoDB (`screening_results` table)
→ External System (React App for email + booking)

---

# 4. ⚙️ Technologies Used

* **Python** → Backend processing
* **AWS DynamoDB** → NoSQL database
* **AWS S3** → File storage (pitch decks)
* **LibreOffice** → PPT → PDF conversion
* **pdfplumber + OCR** → Text extraction
* **LLM API (OpenAI / Groq / Gemini)** → AI evaluation
* **Render** → Deployment

---

# 5. 🔁 Processing Pipeline

### Step 1: Fetch Latest Entry

* Only startups with `status = "submitted"` are fetched
* Sorted using `createdAt` (handled manually due to DynamoDB limitations)

---

### Step 2: File Processing

* Pitch deck downloaded from S3
* Converted from PPT → PDF
* Text extracted using:

  * pdfplumber
  * OCR (for image-based slides)

---

### Step 3: AI Evaluation

* Extracted text sent to LLM
* Model returns:

  * Category-wise scores
  * Red flags
  * Reasoning

---

### Step 4: Decision Logic

Final decision calculated in Python:

* 80+ → Auto-select
* 65–79 → Incubate with conditions
* 50–64 → Pre-incubation
* <50 → Reject

---

### Step 5: Store Results

Stored in `screening_results` table:

* Scores JSON
* Total score
* Decision
* Reasoning
* Email flag

---

# 6. 🧠 Key Design Decisions

### ✅ 1. Decoupled Architecture

* Processing system separated from email & booking system
* Improves scalability and maintainability

---

### ✅ 2. Single Worker Processing

* Only one startup processed at a time
* Prevents race conditions and duplicate processing

---

### ✅ 3. Status-Based Flow

submitted → processing → analyzed
↘ failed

---

### ✅ 4. No Local Storage

* Temporary files only
* Ensures deployment compatibility

---

# 7. ⚠️ Challenges Faced & Solutions

---

### 🔴 Issue 1: DynamoDB Sorting

**Problem:**
DynamoDB does not guarantee order in scan

**Solution:**

* Manually sorted entries using `createdAt`
* Converted mixed date formats into timestamps

---

### 🔴 Issue 2: Mixed Date Formats

**Problem:**
Different formats in `createdAt` caused incorrect sorting

**Solution:**

* Standardized parsing logic
* Converted all formats → timestamps

---

### 🔴 Issue 3: PPT Processing Failures

**Problem:**
Some PPT files failed during conversion

**Solution:**

* Added failure handling
* Marked entry as `failed`
* Continued pipeline without stopping

---

### 🔴 Issue 4: JSON Output from AI

**Problem:**
AI sometimes returned inconsistent JSON

**Solution:**

* Designed strict prompt format
* Moved final decision logic to Python (deterministic)

---

### 🔴 Issue 5: Deployment Complexity

**Problem:**
Multiple services (email, booking, backend)

**Solution:**

* Refactored architecture
* Kept only evaluation engine
* Moved UI + email + booking to React system

---

# 8. 🔄 Architecture Evolution

### Initial Approach:

* Python backend
* Email automation
* Flask booking server
* Calendar integration

### Updated Approach:

* Python → Only evaluation engine
* React system → Handles:

  * Emails
  * Booking
  * Calendar

👉 Result: **Simpler + scalable system**
